# ЛР4 — Kanban и план работ по MVP

## Методологии

**Scrum** организует разработку спринтами фиксированной длины. Команда задает цель спринта, выбирает задачи, проводит планирование, ежедневное обсуждение, review и retrospective. Состав работ и даты помогают оценить результат итерации.

**Kanban** организует непрерывный поток задач. Карточки проходят последовательные состояния, а ограничения WIP помогают завершать начатое. Новая задача берется в работу после освобождения места в активной колонке.

## Выбор и рабочая доска

Для проекта «Модуль» выбран **Kanban**. Требования, макеты, разработка интерфейса и проверка проходят общую последовательность, поэтому состояние каждой задачи удобно видеть на одной доске. Приоритеты можно уточнять по мере готовности зависимостей, не ожидая начала следующего спринта.

Платформа: **GitHub Projects**, связанная с GitHub Issues и репозиторием проекта. [Project](https://github.com/users/akov40320/projects/1) создан по шаблону Kanban и содержит 16 issues. Конфигурация полей и статусов проверена: 14 Done / 2 In Progress. Исходное задание указывает Яндекс Трекер; фактическая замена зафиксирована в [service-mapping.md](../service-mapping.md).

## Колонки и ограничения

**Backlog → To Do → In Progress → Review → Done.** Русские названия ниже поясняют смысл статусов; фактические значения сервиса указаны на английском.

| Колонка | Содержание | WIP |
|---|---|---|
| Бэклог | Все известные задачи и улучшения | Не задан |
| К выполнению | Выбранные приоритетные задачи, готовые к началу | Не задан |
| В работе | Активная реализация | **2** |
| На проверке | Проверка результата по критериям приемки | **1** |
| Готово | Проверенные результаты; CI успешен для изменений приложения | Не задан |

GitHub column limits отображают количество карточек и подсвечивают превышение, но не блокируют перенос технически. При заполненной колонке новая задача не берется: сначала завершается текущая или устраняется затор на проверке. Возврат в **«В работе»** сопровождается комментарием с проблемой и ожидаемым исправлением.

## Ежедневная работа и история

1. Выбрать приоритетную задачу из **«К выполнению»**, проверить зависимости и свободное место по WIP.
2. Перевести карточку в **«В работе»**, создать feature-ветку и указать связь с issue.
3. После реализации добавить ссылку на PR, результаты проверки и передать карточку в **«На проверке»**.
4. Проверить критерии приемки. Замечания записать в issue; при успехе завершить PR и перевести карточку в **«Готово»**.
5. Продолжать ведение доски **в течение всего семестра**, как требует исходное задание. История сервисных действий служит подтверждением движения задач.
