# Модуль — учебный B2B MVP (вариант 4)

Локальное статическое приложение для выбора модульных конструкторов: шесть демонстрационных наборов, три направления, поиск, фильтр бюджета, сортировка, карточки с описанием, расчёт партии и форма заявки. В учебном кабинете доступны просмотр, удаление и JSON-экспорт заявок, а также добавление, изменение, удаление и восстановление каталога.

## Запуск и проверка

Нужен Node.js 22 или новее. Устанавливать зависимости для приложения не требуется. Команды выполняются в каталоге `project`:

```sh
npm start
# Открыть http://127.0.0.1:4173
npm run lint
npm test
npm run build
node scripts/serve.mjs --root dist --port 4173
```

`lint` проверяет синтаксис JavaScript средствами Node, ссылки на локальные ресурсы, уникальность HTML id, наличие используемых DOM-элементов и структуру CSS. Это специальная проверка проекта, а не полный ESLint/HTML-валидатор. `npm test` запускает 16 тестов бизнес-правил на встроенном `node:test`. Сборка копирует приложение в `dist`, очищая предыдущую сборку. Все пути ресурсов относительные, включая размещение Pages в подкаталоге репозитория.

Исходники: `app/index.html`, `app/styles.css`, `app/main.js`; чистые бизнес-правила: `app/domain.js`; SVG-иллюстрации: `app/assets`. Иллюстрации оригинальные, созданы из геометрии локально; воспроизводятся командой `node scripts/generate-assets.mjs`.

## Яндекс Формы

Для опубликованной формы укажите её публичную ссылку в `app/service-config.js` (поле `YANDEX_FORM_URL`). После сборки в блоке заявки появится кнопка «Открыть форму в Яндексе», ведущая в сервис. `lint` проверяет, что ссылка использует HTTPS и домен `forms.yandex.ru`. Пока поле пустое, кнопка скрыта. Локальная форма и расчёт партии доступны независимо от настройки; ответы Яндекс Форм хранятся и просматриваются в самом сервисе.

## Правила и ограничения

- Минимальная партия зависит от позиции: исходно 10, 25 или 20 штук. Максимум — 10000. Количество должно быть целым.
- Скидка в демо: 5% от 50 и 10% от 100 наборов. Экономия округляется до целого рубля. Доставка не рассчитывается.
- Для заявки обязательны имя, компания, корректный email, набор, количество и согласие на локальное сохранение. Телефон и комментарий необязательны.
- Каталог и заявки хранятся в `localStorage` с ключами `modul.catalog.v1` и `modul.leads.v1`, до 100 записей каждого типа. Повреждённый каталог восстанавливается исходным; повреждённые заявки отбрасываются. Экспорт заявок создаёт локальный JSON-файл.
- Данные относятся к браузеру и адресу сайта, не синхронизируются и могут исчезнуть после очистки хранилища. Открытый учебный редактор не содержит авторизации. Backend, реальная отправка заявки, оплата, доставка и продажи отсутствуют. Используйте вымышленные данные.
- Наименование, характеристики, цены и адрес `hello@modul.example` демонстрационные. Проект не связан с LEGO Group.

## Проверка в браузере

Необязательный `scripts/browser-smoke.mjs` использует Playwright из среды проверки, отдельно от приложения. Он запускает собранный сайт на `127.0.0.1:4174`, проверяет фильтры, диалог, ошибки формы, расчёт, сохранение после перезагрузки, редактор, JSON-экспорт, удаление, сброс и отсутствие горизонтального переполнения на ширинах 390 и 320 px. Перед запуском нужна сборка. Укажите `PLAYWRIGHT_MODULE_PATH` (абсолютный путь к `playwright/index.mjs`) и, если требуется, `BROWSER_EXECUTABLE_PATH` (путь к браузеру), затем выполните:

```sh
node scripts/browser-smoke.mjs
```

Результат сохраняется в `../evidence/browser-checks.json`, скриншоты — `../evidence/app-desktop.png` и `../evidence/app-form.png`. Текстовые логи проверок лежат в `project/evidence`. Скриншоты показывают настоящую локальную страницу с вымышленными тестовыми данными. Браузерная проверка не запускается в CI без отдельно установленного Playwright.

Для сохранения результата в другой папке задайте `SMOKE_EVIDENCE_DIR` — например, абсолютный путь к `project/evidence/browser`.

Дополнительный `node scripts/docs-smoke.mjs` в той же среде проверяет документы через `file://`: Kanban-перемещения, ограничения WIP 1/2, восстановление состояния при перезагрузке, встроенные страницы Wiki, локальные ссылки и SVG-макеты. Результат — `../evidence/docs-browser-checks.json`; снимки — `board.png`, `wiki.png`, `wireframes.png` в той же папке.

## CI/CD

Корнем Git-репозитория должен быть каталог **«Готовые лабораторные»**. Канонический workflow находится в `../.github/workflows/ci-cd.yml`: `push` и `pull_request` выполняют lint, тесты и сборку в `project`. После успешного CI при `push` в `main` загружается `project/dist`, и зависимая задача публикует артефакт в GitHub Pages. Публикация из PR или других веток не выполняется.

Перед первым развёртыванием включите **Settings → Pages → Source → GitHub Actions**. Для повторной публикации текущего `main` можно запустить **Actions → CI and GitHub Pages → Run workflow**. Проверка `ci` выполняет все три обязательных шага; `deploy` зависит от её успешного результата. Права публикации выдаются только задаче `deploy`.
